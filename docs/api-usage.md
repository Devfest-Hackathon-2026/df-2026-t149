# API の利用量の測定

この文書は、Places API の呼び出し回数と費用を確かめる手順を説明する。サーバーは呼び出しを機能ごとに数え、開発環境では `GET /api/usage` で回数と料金の目安を返す。

## 費用が発生する API

| API | 区分 | 無料枠（月） | 無料枠を超えた後の料金（1,000 回あたり） | 呼び出す場面 |
|---|---|---|---|---|
| Nearby Search | Enterprise | 1,000 回 | $35 | 未踏サーチ、チェックインの候補、代替提案の周辺検索 |
| Text Search | Enterprise | 1,000 回 | $35 | 代替提案の有名スポットの特定 |
| Place Details（`id`、`location`） | Essentials | 10,000 回 | $5 | チェックインの場所の確認 |
| Place Details（`id`、`displayName`） | Pro | 5,000 回 | $17 | 思い出ログの一覧の名前 |
| Text Search（`id`、`displayName`、`location`） | Pro | 5,000 回 | $32 | 地図を移動する先の検索 |
| Dynamic Maps | Essentials | 10,000 回 | $7 | Web 版の地図（キーを設定したとき） |
| Maps SDK | Essentials | 無制限 | なし | Android 版の地図 |

料金は 2026-11-07 に [公式の料金表](https://developers.google.com/maps/billing-and-pricing/pricing) で確かめた値である。検索の取得項目には `userRatingCount` を含むため、Nearby Search と Text Search は Enterprise 区分になる。無料枠の中であればクレジットは減らないので、少しの試用ではクレジットの残高が変わらない。このため、費用は残高ではなく呼び出し回数から計算する。

## 手順 1：費用をかけずに回数を数える

`PLACES_API_KEY` を設定しないサーバーは、ダミーデータを返しながら、本物なら呼んでいたはずの回数を `simulated` として数える。`mock=1` を付けた呼び出しは本物でも Places API を呼ばないので数えない。

```bash
cd backend && make dev
```

```bash
cd app && flutter run -d chrome
```

アプリを想定する使い方で操作した後に、次のコマンドで回数を表示する。サーバーを起動し直すと回数は 0 に戻る。

```bash
cd backend && make usage
```

`today.simulated.calls` のキーは「種類.機能」の形であり、`listPriceUsd` は無料枠を引かない料金である。

## 手順 2：本物の API で確かめる

本物の API で回数が同じになること、および候補の質を確かめる。Firebase の設定は必要ない。

1. Google Cloud のコンソールで予算アラートを設定し、Places API (New) だけを許可したキーを作成する（[setup.md](setup.md) の 1 章）。
2. `backend/.env.example` を `backend/.env` にコピーし、`PLACES_API_KEY` を記入して、`PLACES_DAILY_LIMIT=30` にする。この上限で 1 日に増える費用は、無料枠を使い切った後でも $1.05 以下である。
3. `cd backend && make real` でサーバーを起動し、手順 1 と同じ操作を行う。
4. `make usage` で `today.real.calls` を確かめる。上限に達すると、サーバーは `429 daily_limit` を返し、アプリは「今日はこれ以上、場所を探せません」と表示する（ダミーデータには切り替えない）。
5. 翌日に、コンソールの「Google Maps Platform > 指標」で Places API (New) の回数を、「お支払い > レポート」で SKU ごとの回数と料金を確かめ、`make usage` の値と比べる。

`GET /api/usage` は `AUTH_MODE=fake` のときだけ公開する。Cloud Run では、回数を Firebase コンソールの Firestore の `usage/{JST の日付}` で読む。インスタンスが入れ替わっても回数は残る。呼び出しごとの記録は Cloud Logging の `places_call` でも検索できる。

## 操作ごとの回数

次の表は、手順 1 の方法で Web 版を操作して数えた回数である。半径の変更と範囲を広げる操作は、同じ検索の処理を呼ぶことをコードで確かめた。

| 操作 | Nearby Search | Text Search |
|---|---|---|
| アプリの起動（地図の最初の検索） | 1 | 0 |
| 地図の「このエリアを探す」、半径の変更 | 1 | 0 |
| 代替提案の検索、範囲を広げる操作 | 3 | 1 |
| チェックインのタブを開く | 1 | 0 |
| 行ったかもしれない場所の候補の読み込み（開いたときに最大 3 件） | 1 件につき 1 | 0 |
| 2 分以内にチェックインのタブを開き直す | 0 | 0 |
| 思い出ログの追加、訪問者数 | 0 | 0 |

起動、チェックインのタブ（滞在 3 件）、代替提案の検索 3 回、エリアの検索 1 回を行う利用では、Nearby Search が 15 回、Text Search が 3 回になる。無料枠を除いた料金に換算すると $0.63 である。

Place Details の回数は、初めてのチェックイン 1 件につき位置の確認が 1 回、思い出ログの一覧や周辺のタイムラインを開くたびに、表示する場所 1 か所につき名前の取得が 1 回である。周辺のタイムラインは 1 回で最大 20 か所を読む。チェックイン済みの場所へのチェックインでは呼ばない。

## 回数を止める仕組み

検索の API は ID トークンを必須にしているので、ログインしていない呼び出しでは Places API を消費しない。

`PLACES_DAILY_LIMIT` はサーバー全体の 1 日の上限であり、`PLACES_USER_DAILY_LIMIT` は 1 人あたりの 1 日の上限である（既定は 30 回で、代替提案の検索は 1 回で 4 回分になる）。回数はチェックインなどと同じ保存先に記録する。どちらかの上限に達すると、未踏サーチと代替提案はダミーデータを返し、チェックインの候補は 503 を返す。アプリはこの 503 を圏外と同じように扱い、ダミーのスポットを候補に出さない。

Place Details は検索と別に数え、位置の確認と名前の取得のそれぞれに、サーバー全体の 1 日の上限 `PLACES_DETAILS_DAILY_LIMIT`（既定は 150 回）がある。1 人あたりの 1 日の上限は全体の上限から決まり、位置の確認は 10 分の 1（既定は 15 回）、名前の取得と地図の移動先の検索は 3 分の 1（既定は 50 回）である。検索と別に数えるのは、思い出ログを開くだけで検索が止まることを防ぐためである。

テストの間だけ上限をゆるめるときは、`PLACES_TEST_UNTIL` に最後の日（JST）を入れる。その日までは 1 人あたりの上限をなくし、検索と Place Details の種類ごとの全体の上限を `PLACES_TEST_DAILY_LIMIT` にする。日付を過ぎると、デプロイし直さなくても元の上限に戻る。自動デプロイは 2026-11-16 まで、全体 300 回にしている（検索が毎日 300 回に達すると、7 日間で無料枠を超えた分が約 40 ドル）。位置の確認が上限に達するとチェックインの API は 503 を返し、アプリは記録を端末に残して送り直す。名前の取得が上限に達すると、一覧は名前なしで記録を返す。
