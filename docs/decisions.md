# 技術を選んだ理由（Own the Why）

AI の提案をそのまま採らず、比べて選んだ理由を残します。提出ドキュメントの「選定理由・メリット/デメリット」にそのまま使います。

**書き方**：1 項目につき「選んだもの・捨てた案・理由・弱み」。決めた人と日付も書く。迷っている項目は「未決」に置く。

---

## D-001 アプリは Flutter で作る

- **選んだもの**：Flutter（Web と Android を 1 つのコードで）
- **捨てた案**：React などの Web だけ（実地検証で使うスマホアプリにしにくい）、Android ネイティブ（Web で審査員に触ってもらえない）
- **理由**：審査員にはデプロイした Web の URL で、実地検証では Android の実機で、同じコードを動かせる。Google 技術としても説明しやすい
- **弱み**：Web 版の地図は Maps JavaScript API が別に必要。ビルドの待ち時間が長い
- 決めた人・日付：チーム（0 日目）

## D-002 Places API はサーバー（Cloud Run）から呼ぶ

- **選んだもの**：Go のサーバーを Cloud Run に置き、アプリはサーバーだけを呼ぶ
- **捨てた案**：アプリから Places API を直接呼ぶ
- **理由**：
  - API キーがアプリに入らない（審査項目の「安全性」）
  - 1 日の呼び出し回数をサーバーで止められる（クレジット $20 を守る）
  - 未知度スコアの計算を 1 か所にまとめられ、B がテストしやすい
  - ルールの必須条件「実行に Cloud Run などを使う」をはっきり満たす
- **弱み**：サーバーを 1 つ運用する手間。呼び出しが 1 段増える
- 決めた人・日付：A（11/5）

## D-003 サーバーは Go で書く

- **選んだもの**：Go
- **捨てた案**：Dart（shelf）（2026-11-05 に選んだが、2026-11-06 に変更）、Python（FastAPI）、TypeScript（Node）
- **理由**：
  - Google の製品で、GDGoC のハッカソンの「Build with Google Cloud」に合う
  - 軽量で安定しており、ビルドするとシングルバイナリになる。Cloud Run に載せるコンテナが小さく、起動が速い
- **弱み**：該当なし
- 決めた人・日付：A（リーダー）、2026-11-06（D-003 の初回の決定は 2026-11-05、Dart の採用）

## D-004 Web 版は Firebase Hosting で公開し、`/api` を Cloud Run に転送する

- **選んだもの**：Firebase Hosting の rewrites で `/api/**` を Cloud Run へ
- **捨てた案**：Cloud Run で Web も配る、別のドメインから API を呼ぶ
- **理由**：同じオリジンになるので CORS の設定がいらない。Hosting は静的ファイルの配信が速く、無料枠が大きい
- **弱み**：Hosting と Cloud Run の 2 か所にデプロイが必要
- 決めた人・日付：A（11/5）

## D-005 チェックインと思い出ログは API サーバーが Firestore に保存し、匿名ログインを使う

- **選んだもの**：Firebase Authentication（匿名）＋ Firestore。アプリは cloud_firestore を使わず、ID トークンを付けて API サーバーを呼ぶ
- **捨てた案**：アプリから Firestore を直接読み書きする（0 日目に選んだが、2026-11-06 に変更）、Cloud SQL（サーバーの運用が増え、常時料金がかかる）、ログインなし（誰の記録か区別できない）
- **理由**：登録なしですぐ使え、何人目かはトランザクションで重ならずに決められる。開拓者のバッジは何人目かで決まるので、順番はサーバーが受け取った順に決め、本人が偽れないようにする。日時は圏外で記録した訪問の日付がずれないようアプリの値を受け取るが、順番には影響しない
- **弱み**：匿名ログインは端末を変えると記録が引き継げない
- 決めた人・日付：D（2026-11-06）（初回の決定は C、0 日目）

## D-006 Places API の内容は保存しない

- **選んだもの**：Firestore には place ID と訪問者数だけを保存し、評価、口コミ数、住所、名前は保存しない。思い出ログの名前は、一覧を返すときに Place Details で読む
- **捨てた案**：思い出ログに `placeName` を保存する（11/7 に一度選んだが、規約と食い違うため同日に変更）、1 か月ごとに名前を更新する（保存していることに変わりがない）
- **理由**：Google Maps Platform の利用規約で、place ID 以外のコンテンツの保存が制限されているため。ダミー JSON も架空のデータにする
- **弱み**：思い出ログを読むたびに Place Details の Pro 区分（月 5,000 回まで無料）を消費する。Places API の失敗時と圏外では名前を表示できない。送信するまでの未送信の記録には、一覧に表示するため端末に名前が残る
- 決めた人・日付：チーム（0 日目）、`placeName` の保存をやめる判断は B（11/7）

## D-007 API キーや Firebase がなくても動くようにする

- **選んだもの**：サーバーはキーがなければダミー JSON を返す。アプリは API サーバーに接続できないときと API がまだないときに同梱したダミーデータを表示し、Firebase の設定がなければメモリに保存し、地図のキーがなければ簡易地図を表示する。どれも使えるようになれば自動で切り替わる
- **理由**：初日から全員が同じ画面で開発を始められる。デモ当日に API が失敗しても、切替スイッチでダミーを見せられる（デモの保険）
- **弱み**：本物とダミーで動きがずれないよう、ダミー JSON を本物の形に合わせ続ける必要がある
- 決めた人・日付：A（11/5）

## D-008 開発はこの非公開リポジトリで行い、CI は GitHub Actions で回す

- **選んだもの**：開発用リポジトリ（非公開）で開発し、プルリクエストごとに Actions でテストと Web ビルド。最終版だけを運営の提出用リポジトリに 1 コミットで送る
- **捨てた案**：提出用リポジトリで直接開発する（Actions と Pages が使えず、履歴ごと公開される）
- **理由**：運営のおすすめどおり。マージ前に壊れていないかを自動で確かめられ、毎晩「main はデモできる」を守りやすい。履歴に秘密情報が残っても公開されない
- **弱み**：提出のときに中身を写す手間がかかる（最終版のファイルだけを 1 コミットにまとめて送る）
- 決めた人・日付：A（11/5）

## D-009 フォントは google_fonts で読み込む

- **選んだもの**：google_fonts（8 系）で、全ての文字に Zen Kaku Gothic New を使う。google_fonts の 9 系は Flutter 本体とは別の `material_ui` パッケージの `TextTheme` を返し、アプリの `ThemeData` に渡せないため、8 系に固定している
- **捨てた案**：特になし
- **理由**：端末やブラウザによらず、日本語を同じ書体で読みやすく表示できるため
- **弱み**：フォントを実行時に fonts.gstatic.com から取得するため、通信できない環境では端末の標準のフォントで表示される。Zen Kaku Gothic New は 1 つの太さで約 2.3MB あり、400 と 700 の2つで約 4.7MB を初回に取得する
- 決めた人・日付：B（11/5）

## D-010 Google マップの道順は url_launcher で開く

- **選んだもの**：url_launcher で、場所の詳細から Google マップの道順（`https://www.google.com/maps/dir/?api=1&destination=緯度,経度`）を開く
- **捨てた案**：特になし
- **理由**：道案内を自分たちで作らずに、利用者が使い慣れた Google マップで道順を確かめられるため。導入もパッケージ 1 つで済む
- **弱み**：Android 11 以降で URL を開くアプリを調べるため、AndroidManifest.xml に `queries` の追加が必要になる
- 決めた人・日付：B（11/5）

## D-011 キーカラーは端末の壁紙の色と、利用者が選んだ色からも作れるようにする

- **選んだもの**：dynamic_color（1 系）で Android 12 以降の壁紙の色を取得し、shared_preferences で選んだテーマとキーカラーを端末に保存する。dynamic_color の 2 系は google_fonts の 9 系と同じく `material_ui` の型を使い、アプリの `ThemeData` と組み合わせられないため、1 系に固定している
- **捨てた案**：特になし
- **理由**：利用者の端末に合った色で表示し、好みの色も選べるようにして、アプリに親しみを持ってもらうため
- **弱み**：選んだ色が明るいと白い文字が読めなくなるため、コントラスト比が 4.5 に届かない色は、主な色をキーカラーから作った濃い色に置き換えて表示する
- 決めた人・日付：B（11/5）

## D-012 チェックインの現在地に geolocator、滞在の記録に WorkManager を使い、未送信の記録を shared_preferences に保存する

- **選んだもの**：geolocator（14 系）で現在地を読み、workmanager（0.10 系）で約 15 分ごとに位置を測定する。未送信の記録と滞在の記録は、すでに使っている shared_preferences に JSON で保存する
- **捨てた案**：通知付きのフォアグラウンドサービス（2 分ごとに測定できるが、記録中は通知を消せない）
- **理由**：記録中に常設の通知を出さないため（B、11/7）。Google Play に公開しないので、ACCESS_BACKGROUND_LOCATION の審査を考えなくてよい
- **弱み**：利用者が位置情報を「常に許可」にする必要がある。測定の間隔が長く、省電力機能でさらに空くことがあるので、短い滞在を記録できないことがある。アプリを強制的に閉じると、次に開くまで記録できない。滞在の判定の値（半径 100 m、10 分）は実地で調整していない
- 決めた人・日付：B（11/7）

## D-013 CI は dorny/paths-filter で変更したファイルに関係するジョブだけを動かす

- **選んだもの**：`.github/workflows/ci.yml` の中で dorny/paths-filter を使い、backend と app のジョブをそれぞれの変更があるときだけ動かす。Firestore エミュレーターのテストは保存処理を変えたときだけ動かす。main への push では動かさない
- **捨てた案**：ワークフローのファイルを分けて `paths` で絞る（必須のチェックにすると、動かなかったワークフローの結果を待ち続けて Pull Request を止める）
- **理由**：CI を無駄に回さないため
- **弱み**：API の形を変える Pull Request で片方のフォルダだけを変えると、もう片方のテストが動かない
- 決めた人・日付：B（11/7）

## D-014 チェックインでは場所の実在と距離をサーバーで確かめる

- **選んだもの**：アプリは場所から 500 m 以内のときだけチェックインの画面を開き、現在地または滞在の位置をサーバーへ送る。サーバーは Place Details（`id`、`location`）で場所の実在と距離を確かめる。ダミーの場所は確かめず、端末のメモリだけに記録する
- **捨てた案**：実在だけを無料の IDs Only の Place Details で確かめる（API を直接呼ぶと遠くの場所に記録できる）、確認を入れない（任意の ID に訪問者数を作れる）
- **理由**：Places API のキーをサーバーだけに持たせ、アプリが必要とする API キーの情報を減らすため。あわせて、距離をサーバーで確かめることで、遠くの場所への記録や存在しない場所の訪問者数を作れないようにする
- **弱み**：位置は端末から送るので偽装を防げず、匿名アカウントを複数作って人数を増やすことも防げない。代表地点から 500 m より遠い入口がある広い公園では、その入口からチェックインできない。本物のデータでは、会場から遠い場所にデモでチェックインできないので、デモでは設定の「ダミーデータを使う」を使う
- 決めた人・日付：B（11/7）

## D-015 新しい画面を別のフォルダに作り、設定で切り替える

- **選んだもの**：`app/lib/ui_v2/` に新しい画面を作り、設定の画面と `app_config.json` の `newUi` で切り替える

- **弱み**：切り替えを残す間は 2 つの画面を保守する。新しい画面に決めたら今の画面を消す
- **その後**：11/10 に新しい画面に決め、今の画面と切り替えを消して、画面を `app/lib/features/` の機能ごとのフォルダに移した
- 決めた人・日付：B（11/7）

## D-016 周辺のタイムラインをチェックインの地点の区画で探す

- **選んだもの**：距離を確かめたチェックインの地点を 5 文字の geohash にして保存し、その区画と周囲の 8 区画で公開された記録を探す。記録の公開は利用者が記録ごとに選び、既定は自分だけにする
- **捨てた案**：場所の位置を保存する（Places API の緯度と経度は 30 日までしか保存できない）、Nearby Search の結果の place ID で探す（探した場所にない記録が出ない）
- **理由**：Places API の緯度と経度を保存せずに（利用規約）周辺の記録を探せるため。記録の公開を利用者が記録ごとに選べるようにし、既定を自分だけにして、意図せず公開されないようにする
- **弱み**：匿名アカウントを複数作ると、3 人分の報告で他の人の記録を隠せる。表示名は設定できず、uid から作った符号を表示する。開くたびに場所の名前を読むので Place Details の回数を消費する
- 決めた人・日付：B（11/7）

## D-017 Geminiちゃんは Vertex AI の Gemini で意図と理由だけを作り、場所は今の検索で探す

- **選んだもの**：`POST /api/assistant` を足し、Go から Vertex AI の Gemini（Go SDK `google.golang.org/genai`、既定のモデルは `gemini-3.1-flash-lite`）を 1 回の相談で最大 2 回呼ぶ。1 回目で一言の意図と地名とジャンルを JSON で読み取り、今の Nearby Search・代わりに行くならここ・地点の検索で場所を探し、2 回目で候補の番号を選ばせて理由を書かせる。失敗・上限・8 秒の待ちでは、キーワードで答える簡易版に切り替える。画面はチャットにせず、地図の右下のボタンから開くシートに、最新の一言と答えだけを出す
- **捨てた案**：
  - AI Studio の Gemini API（クレジットが使えない）
  - Gemini に場所を考えさせる、または Grounding with Google Maps を使う（存在しない場所を勧めるおそれ、料金が高い）
  - 代替提案の応答に推薦文を足すだけ（「追加提案」の案。検索の補助にならない）
  - チャットの画面（履歴を並べると地図の操作から離れる。依頼の後にすることは「地図で見る」「場所を開く」に限られる）
- **理由**：Gemini の出力を有効に用いるため。一言から意図を読み取るという Gemini の得意な部分に使い、場所そのものは実在する検索結果から選ぶ
- **弱み**：（D-036 で見直し：Places API の結果は Gemini に渡さず、理由の文はテンプレートで作るようにした）Places API の名前や種類を Gemini のプロンプトに入れる（保存はしない）。規約上の扱いは要確認。理由の文は Gemini が書くので、渡していない事実を書くことがある（プロンプトで禁じ、60 文字で切る）。2.5 Flash-Lite は Vertex AI で 2026-10 に提供終了したので、デプロイ前にモデル ID を確かめる。ローカルでは gcloud の ADC がないと本物を試せない
- 決めた人・日付：D（11/7）

## D-018 実績はアプリで思い出ログから計算する

- **選んだもの**：`app/lib/features/achievements/` に実績の定義（19 件。うちシークレット 8 件、段階（ブロンズ・シルバー・ゴールド）のある実績 10 件。★1 を付けることを勧める実績は置かない）を置き、`CheckinRepository.watchLogs()` の思い出ログから進み具合と解除の日時を計算する。新しく保存するデータはない
- **捨てた案**：サーバーで計算する `GET /api/achievements`（一度作ったが消した。Firebase を使わない設定の端末に保存した記録と、圏外で残してまだ送っていない記録を数えられない）、Firestore に解除の記録を保存する（構造を変える必要があり、締切までに C と調整できない）
- **理由**：圏外で残してまだ送っていない記録や、Firebase を使わない設定の端末の記録も数えられ、保存するデータを増やさずに済むため
- **弱み**：端末の値から計算するので、利用者が記録を偽れる（順番はサーバーが決めるので、開拓者などは偽りにくい）。チェックインだけで思い出ログのない場所は数えない。解除の演出はチェックインの画面から残したときだけ出す（残す前の記録を読み終わる前に残したときは省く）
- 決めた人・日付：D（11/7）

## D-019 代替提案は有名スポットの周囲の 3 地点を人気順で検索する

- **選んだもの**：有名スポットから半径の 40% だけ離れた 3 地点を中心に、主な種類で絞った Nearby Search を人気順で行い、`containingPlaces`、距離、口コミ数で絞り込んで近い順に並べる。
- **捨てた案**：有名スポットを中心に近い順で探す案は、敷地内の門や像で 20 件が埋まる。有名スポットを中心に人気順で探す案は、近隣の有名な場所で 20 件が埋まる。
- **理由**：本物の Places API で両案と比べ、3 地点の検索だけが独立した知られていない場所を十分な件数で返した（B、11/7）。
- **弱み**：検索 1 回の Places API の呼び出しが 2 回から 4 回に増える。公園を探す場合は、住宅地の小さな公園が候補に多く入る。

## D-020 Google アカウントでのログインを必須にし、ニックネームとアイコンで表示する

- **選んだもの**：Firebase Authentication の Google アカウントでのログインを必須にする。Web 版は `signInWithPopup`、Android 版は google_sign_in 7.x（Credential Manager）で受け取った ID トークンを Firebase に渡す。サーバーは匿名ログインのトークンを `login_required` で拒否する。タイムラインの投稿者は、利用者が決めたニックネーム（必須、1〜20 文字）と、アプリが用意した 12 種類のアイコンで表示する。
- **捨てた案**：匿名ログインのまま使う案（端末を変えると記録を引き継げない）、匿名アカウントを Google アカウントに紐付けて記録を引き継ぐ案（利用者がまだいないため、引き継ぐ記録がない）、Google アカウントの名前と写真を表示する案（実名と顔写真の場合がある）、`signInWithRedirect`（サードパーティのストレージをブロックするブラウザで動かず、web.app では authDomain の変更も必要になる）、アイコンの画像をアップロードする案（不適切な画像への対応と Cloud Storage の設定が必要になる）。
- **理由**：ログインしなければ使えないようにしたい。実名の Google アカウントもあるため、ニックネームの設定を必須にする（B、11/8）。
- **弱み**：Google アカウントを持たない人は使えない。Android 版は Firebase に SHA-1 と SHA-256 を登録しないとログインできない。ニックネームの内容は確かめないため、不適切な名前は報告で対応する。

## D-021 シェアと紙吹雪は、新しいパッケージを入れずに作る

- **選んだもの**：シェアは X と LINE の投稿の画面の URL を `url_launcher`（導入済み）で開き、文のコピーも用意する。紙吹雪は `CustomPainter` で描いた（11/9 に D-027 のチェックインスタンプに置き換えた）。
- **捨てた案**：`share_plus`（Android の共有シートを出せるが、依存と権限の確認が増える）、`confetti` パッケージ（Web 版の読み込みが増える）。
- **理由**：依存するパッケージと権限の確認を増やさず、Web 版の読み込みを軽く保って、アプリの動作を安定させるため
- **弱み**：Android でも端末の共有シートは出ず、X と LINE 以外のアプリへはコピーして貼る必要がある。画像はシェアできない。

## D-022 広い範囲は複数の地点で探し、人気度の幅で探し方を変える

- **選んだもの**：未踏サーチの半径を 50km（Nearby Search の上限）まで広げる。3km 以上の範囲は、中心と中心から半径の 6 割の 3 地点の計 4 地点で探す。ジャンルを選んでいないときは、訪れられる種類に絞って探す（候補が少なく、ごく近くにしか出ないという指摘、11/9）。`popularity`（称号の段階の最小と最大）に定番か超有名を含むと人気順でも探し、幅の中の場所を先に並べる。
- **捨てた案**：広い範囲を 1 回の近い順で探す（中心のまわりの 20 件で埋まる）、1 回の人気順で探す（有名な場所で埋まる）、地点を 7 つにする（1 人あたりの 1 日の上限 30 回をすぐに使い切る）。
- **理由**：検索結果が範囲の中心のまわりの一か所に集中するのを防ぎ、広い範囲から知られていない場所を拾うため
- **弱み**：広い範囲の検索は 1 回で Places API を 4 回呼ぶ。4 地点の円の間には探さない隙間があり、範囲の全体をくまなく探すわけではない。

## D-023 ★評価は当たり・ハズレと両立させる

- **選んだもの**：思い出ログに `rating`（★1〜5）を足し、サーバーが★3 以上を当たり（`verdict: hit`）として数える。場所ごとの★の合計と数を 1 人 1 票で集計する。★評価のない古い記録は、当たりを★4、ハズレを★2 として表示する。
- **捨てた案**：`verdict` をなくして★だけにする（配布済みのアプリから送れなくなり、保存済みの集計を作り直す必要がある）。
- **理由**：当たり/ハズレの評価は、店や神社の側に見えると悪評を広めているようで印象が悪いため、★評価にした（11/9）。同じ理由で、★の言葉は自分の感じ方として書き（★1「自分には合わなかった」、★2「まあまあ」）、シェアする文には★4以上だけを入れ、検索結果にハズレの数を出さない
- **弱み**：★3 を当たりとして数えるため、「ふつう」も当たりに入る。古い記録の★は推定の値。タイムラインでは、公開した記録の★は低くてもほかの人に見える

## D-024 遠くの地域の一覧はアプリに持つ

- **選んだもの**：定番の地域と、そこに行ったことがある人に次の旅に勧める地域（紹介の文付き）を `app/lib/features/regions/regions.dart` に持ち、選ぶと地図を動かして 20km の範囲で探す。地名でも調べられる（`GET /api/locate`）。どの地域も紹介する相手なので、「〇〇より〇〇がいい」「〇〇は混む」のように比べて下げる言い方はしない（失礼に当たる可能性があるため。11/9 の指摘）。
- **捨てた案**：Gemini に地域を選ばせる（呼び出しの回数が増え、答えが毎回変わる）、Places API で地域を探す（地域の「知られていなさ」を口コミ数で表せない）。
- **理由**：呼び出しの回数と費用を増やさず、毎回同じ内容を出せるため。地域の紹介の文の言い方（ほかの地域を下げない）をチームで確かめてから載せられる
- **弱み**：地域と理由はチームが選んだもので、増やすにはアプリを更新する。

## D-025 ハプティクスは Flutter の HapticFeedback で鳴らし、設定でオフにできる

- **選んだもの**：`app/lib/core/haptics.dart` から Flutter の `HapticFeedback` を呼ぶ。★を選んだとき（★が多いほど強く）、人気度のスライダーの目盛り、何人目かが決まったとき、祝う画面の数え上げと解除のとき、主なボタンで振動させる。設定の画面の「振動（ハプティクス）」でオフにでき、端末に保存する（既定はオン）。
- **捨てた案**：`vibration` パッケージ（振動の長さと強さを細かく決められるが、Android の VIBRATE の権限と依存が増える）。
- **理由**：Duolingo のように操作の手応えを返したい。振動が苦手な人や場所のために、オフにできるようにする（11/9）
- **弱み**：Android は端末の「タッチ操作時のバイブ」がオフだと振動しない。強さは端末ごとに違う。iPhone の Safari では Web 版は振動しない。

## D-026 場所の写真は Places API の画像の URL をアプリに渡す

- **選んだもの**：サーバーが Place Details（`photos`）と Place Photos（`skipHttpRedirect=true`）を呼び、API キーを含まない画像の URL と撮影者をアプリに返す。1 つの場所で最大 4 枚。
- **捨てた案**：画像をサーバーで中継する（Cloud Run の通信量が増える）、アプリから Places API を直接呼ぶ（API キーがアプリに入る）、画像を保存する（Google Maps の規約で保存できない）。
- **理由**：場所の詳細で写真を見たいという要望があったため（11/9）
- **11/9 の判断**：単価が高いので、いったん止める。サーバーの環境変数 `PLACES_PHOTOS=on` でだけ使う（既定は止める。自動デプロイでは渡していない）
- **弱み**：詳細を開くたびに Place Details 1 回と Place Photos 最大 4 回の料金がかかる。単価は `backend/internal/usage/usage.go` に入れたが、使い始める前に公式の料金表で確かめ直す。

## D-027 祝う演出は「チェックインスタンプ」とメダルにし、強い振動は端末の振動の機能で鳴らす

- **選んだもの**：紙吹雪をやめ、御朱印のような朱色の「チェックインスタンプ」が押される演出にする（`app/lib/core/widgets/stamp_celebration.dart`）。前にも来た場所・はじめての場所・1人目（金色、光の筋、「一番乗り」）の3段階で派手さを変え、通常のチェックインでも押す。実績の解除はメダルが回って現れ、光が横切り、星が飛び散る（`MedalReveal`）。強い振動は Android の端末の振動の機能（`MainActivity` の `uramichi/haptics`、`VIBRATE` の権限）で強さと長さを決めて鳴らし、Web はブラウザの Vibration API、どちらも使えなければ Flutter の振動を続けて鳴らす。
- **捨てた案**：紙吹雪（どのアプリにもあり、ウラミチらしさがない）、Lottie などのアニメーションのパッケージ（素材を作る時間と依存が増える）、`vibration` パッケージ（自分で書く量は少なく、依存を増やさない）。
- **理由**：紙吹雪ではないオリジナルの演出と、もっと激しい振動が欲しいという要望があったため（11/9）
- **弱み**：iPhone は Flutter の振動だけで、強さを決められない。スタンプの文字は端末のフォントで描くので、機種によって見た目が少し違う。

## D-028 Instagram へは、スタンプの画像を端末の共有の画面から送る

- **選んだもの**：チェックイン完了の画面のチェックインスタンプと場所の名前の部分を PNG にし、`share_plus` で端末の共有の画面を開く。利用者が Instagram（フィード・ストーリーズ・DM）を選ぶ。Instagram は投稿に文を入れないので、シェアする文はクリップボードにコピーしておく。
- **捨てた案**：Instagram のストーリーズに直接送る（Meta のアプリ ID の登録と、Android の Intent を自分で書く必要がある）、URL で投稿の画面を開く（Instagram には X や LINE のような投稿用の URL がない）。
- **理由**：Instagram でも共有したいという要望があったため（11/9）
- **弱み**：共有の画面で Instagram を選ぶ手間が1つ増える。画像は画面に見えているスタンプをそのまま写すので、演出の途中の姿になることがある。

## D-029 架空の場所（ダミーデータ）は利用者に見せない

- **選んだもの**：API キーのあるサーバーは、Places API が失敗しても 1 日の上限に達してもダミーに切り替えず、`503 places_unavailable` か `429 daily_limit` を返す。アプリも接続先があればダミーに切り替えず、理由ともう一度試す操作を示す。設定の「ダミーデータを使う」と、エラーの画面の「ダミーデータで見る」はなくす。ダミーデータは、API キーのない開発用のサーバーと、接続先のない開発用のビルドだけで使う。
- **捨てた案**：今までどおりデモの保険としてダミーに切り替える（架空の場所が本物のように見え、行っても存在しない）。
- **理由**：ダミーデータをもう使わないでほしいという要望があったため（11/9）
- **弱み**：通信できないときや上限に達したときは、地図に何も出ない。
- **その後**：審査で現地に行けなくてもチェックインを試せるよう、設定に「デモデータで動かす」を置いた。オンのあいだは架空の場所だけを使い、サーバーにも Google にも問い合わせない。オフのときはデモデータを使わず、本物の場所と架空の場所は混ざらない

## D-030 実績のバッジは、花形の七宝のピンバッジにする

- **選んだもの**：実績のバッジを、8枚の花びらの形に切り抜いた七宝（エナメル）のピンバッジにする（`AchievementBadge`）。金属のふち、色のガラス質の面、左上のつやの光を描く。まだ解除していない実績は、色の付いていない灰色のピンにする。
- **捨てた案**：丸いメダル（明るい背景で色の光が濁る）、白いふちのステッカー（11/9 にいったん選んだが、ピンバッジに変えた）、御朱印帳、切符、刺しゅうワッペン、千社札。
- **理由**：6案を見比べ、ステッカーを試したあとでピンバッジを選んだ（11/9）
- **弱み**：形が細かいので、とても小さく表示すると花びらがつぶれて丸に見える。

## D-031 効果音は自作の WAV を同梱し、audioplayers で鳴らす

- **選んだもの**：チェックイン（スタンプを押す音）・実績の解除・★・お気に入り・保存・地図の主なボタンに効果音を付ける。音は `scripts/make_sounds.py` で正弦波と雑音から合成した WAV（`app/assets/sounds/`、合わせて約 140 KB）にし、`audioplayers` で鳴らす（`app/lib/core/sounds.dart`）。マナーモードでは鳴らさず、ほかのアプリの音楽を止めずに重ねる。設定の画面の「効果音」でオフにできる。
- **捨てた案**：フリー素材の効果音（ライセンスの確認と著作物利用シートの記入が増える）、`just_audio`（BGM や長い音向けで、短い音を何度も鳴らすには重い）、`flutter_soloud`（ネイティブのビルドが増える）、端末のシステム音（`SystemSound`。Android ではクリック音しか選べない）。
- **理由**：権利の心配がなく、音をコードで直して作り直せる。振動と同じ場所で鳴らすので、祝う演出と揃う
- **弱み**：合成の音なので、録音した素材より素朴に聞こえる。Web ではブラウザの決まりで、最初の操作の前は鳴らない。

## D-032 日本語の説明文は文節の境界で折り返す

- **選んだもの**：`budoux_dart` の日本語モデルで文節の境界を推定し、共通の状態表示の説明文に使う。
- **捨てた案**：Flutter の既定の折り返しだけを使う案。
- **理由**：文節の途中で改行されにくくし、説明文を読みやすくする（B、2026-11-10）。
- **弱み**：境界の推定は常に正しいとは限らない。絵文字や明示的な改行を含む文章は Flutter の折り返しを使う。

## D-033 Web 版で地図の上の部品の操作を pointer_interceptor で地図に渡さない

- **選んだもの**：`pointer_interceptor` で、広い画面の結果パネル、パネルの開閉のボタン、縦のタブを包む。
- **捨てた案**：地図の上に透明な HTML の要素を重ねる処理を自作する案。
- **理由**：地図のパッケージ（google_maps_flutter_web）の README が案内している方法であり、自作するより確実である（B、2026-11-10）。
- **弱み**：包んだ部品ごとに HTML の要素が1つ増える。Android 版では何もしないため、効果は Web 版に限られる。

## D-034 記録の写真は縮小して Firestore に保存し、API サーバーを通して返す

- **選んだもの**：チェックインの画面で `image_picker` で写真を撮るか選び、長い辺を 1280px・JPEG の画質 80 に縮めてから `POST /api/photos` で送る。サーバーは中身の先頭のバイトで種類を確かめ（JPEG・PNG・WebP、900KB まで）、Firestore の `photos/{id}` に保存する。ID は推測できないランダムな値で、`GET /api/photos/{id}` はログインした人だけが読める。アプリは ID トークンを付けて読み、手元で表示する。
- **捨てた案**：Cloud Storage に保存する（バケット・権限・署名付き URL の設定が増える）、アプリから Storage に直接上げる（Firestore と同じく、アプリから Firebase の保存先を触らない決まりに反する）、元の大きさのまま送る（通信量が多く、Firestore の1件の上限 1MiB を超える）。
- **理由**：ハッカソンの期間で、新しいサービスの設定を増やさずに済む。保存先の決まり（アプリは API だけを呼ぶ）を崩さない
- **弱み**：1枚 900KB までで、元の画質は残らない。写真が増えると Firestore の読み取りと容量の費用が Storage より高くなる。投稿の数が増えたら Cloud Storage へ移す。

## D-035 通知は端末の中だけで出す（flutter_local_notifications）

- **選んだもの**：`flutter_local_notifications` で、バックグラウンドの測定（WorkManager）が同じ場所での滞在を見つけたときに「チェックインしませんか」と知らせる。自分の口コミへの反応は、アプリに戻ったときに数え、増えていれば画面の中で知らせる。設定の画面の「通知」でオフにできる。Web 版では端末の通知を出さない。
- **捨てた案**：Firebase Cloud Messaging でサーバーから送る（反応が付いた瞬間に届くが、端末のトークンの保存・送信の処理・Web の Service Worker の設定が増える）、Web 版でも flutter_local_notifications の Web 版を使う（Flutter の Service Worker を差し替えるため、Firebase Hosting の配信と合わせて確かめる必要がある）。
- **理由**：サーバーの変更なしで始められ、滞在の知らせは端末の中で完結する
- **弱み**：反応の知らせはアプリを開くまで届かない。Android は WorkManager の間隔（15分）より早くは知らせられない。

## D-036 Gemini には利用者の発言だけを渡し、Places API の結果は渡さない

- **選んだもの**：Geminiちゃんで Gemini に任せるのは、利用者の一言から意図（探す・代わり・移動・会話）、地名、ジャンルを読み取ることだけにする。渡すのは利用者の発言だけで、アプリの答え（場所の名前を含む）は会話の履歴からも除く。勧める理由の文は、口コミの数・称号・距離からテンプレートで作る。名前の変わった停留所を Gemini に選ばせて地図の検索結果に残す機能はやめ、停留所は除く。あわせて、ログインと設定の画面に Google マップの追加利用規約と Google プライバシー ポリシーへのリンクを置き（規約 3.2.2(a)）、地図の外に場所の名前を出す画面に「Google Maps」の出典を付けた。
- **捨てた案**：Vertex AI の Grounding with Google Maps や Maps Experience Agent Tools に切り替える（規約の例外の形でいちばんきれいだが、設定と料金が増え、ハッカソンの期間では確かめきれない）、今のまま進めてリスクを書いておく（規約 3.2.3(c)「Google Maps Content から内容を作らない」に当たる可能性が高い）。
- **理由**：規約の本文に当たる可能性が高い使い方をやめ、Gemini の役割を発言の読み取りに絞れば、規約の心配なく続けられる
- **弱み**：理由の文がどの場所も似た言い回しになり、希望に合わせた書き分けができない。名前の変わった停留所を見つける楽しみがなくなる。規約の解釈は私たちの読み方で、法的な判断ではない（審査やリリースの前に Google Maps Platform のサポートに確かめる）。Grounding with Google Maps に移れば、理由の文を Gemini に書かせる形に戻せる。
